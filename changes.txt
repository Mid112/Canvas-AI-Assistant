1a. Chat window layout (143c9b1e) — bugs #1, #10
--------------------------------------------------------------------------------
FILES
    app/frontend/src/components/chat/ChatInput.tsx
    app/frontend/src/components/chat/DraftWorkspacePanel.tsx
    app/frontend/src/pages/Instructor/InstructorAssistantPage.tsx
    app/frontend/src/pages/Instructor/InstructorAssistant/InstructorAssistantHeader.tsx

WHAT AND WHY
    The assistant page sized its chat area with a hardcoded viewport formula,
    min-h-[min(50.5rem,calc(100vh-23.5rem))] and a matching max-h. Every panel
    stacked above the chat (saved drafts, deferred requests, banners) ate into
    that fixed budget, so with a few saved drafts the message input scrolled
    off the bottom entirely and the page became unusable.

    Replaced the magic numbers with a flex contract:
      - the grid container is min-h-0 flex-1 — it claims whatever the panels
        above do not need, instead of a fixed height computed from nothing
      - ChatInput's wrapper became shrink-0, so the input is never the thing
        that gets compressed
      - DraftWorkspacePanel became collapsed-by-default and its list bounded
        at max-h-64 with overflow-y-auto

ARCHITECTURE DELTA
    Vertical space moved from "each component guesses its share of the
    viewport" to "one flex parent owns distribution; children declare whether
    they shrink." Scrolling is now always INSIDE a bounded child, never on the
    page frame.

*** SRP WARNINGS ***
  ! DraftWorkspacePanel owns ONLY its own bounded scroll region. If you add a
    new panel above the chat, give it shrink-0 and bound its own content. Do
    NOT reintroduce a viewport-relative height on the chat container to
    compensate — that is the exact bug this fixed, and it will regress the
    moment anyone adds a fourth panel.
  ! ChatInput must stay shrink-0. Removing it makes the input the flex
    casualty again and it silently squeezes to zero height rather than erroring.

WHAT AND WHY
    ONE FILE WAS DOING TWO UNRELATED JOBS, and they were conflated:

      Mechanism A — inbound PII minimization (CORRECT, untouched)
        llm_student_candidates, llm_safe_student_dict, llm_safe_submission_dict,
        _PII_KEYS. Strips email / login_id / sortable_name BEFORE payloads go
        to the LLM provider. This is the actual privacy control.

      Mechanism B — outbound fact grounding (THE BUG)
        ground_assistant_result rewrote the text the INSTRUCTOR reads,
        substituting "[grade redacted]" and '"[name redacted]"'. This ran on
        the wrong end of the pipe. It destroyed two classes of legitimate
        content:
          - Quoted strings: the pattern could not distinguish a Canvas
            assignment title from the message body the instructor themselves
            typed, so "send X to the class" came back with X blanked out —
            hiding the very text they were being asked to approve (bug #2).
          - Aggregates: facts.grades only ever holds individual fetched
            scores, so an average/rate/percentile is unrepresentable in it by
            construction and was redacted 100% of the time (bug #13).

    New policy: WARN, DO NOT REWRITE.
      - Grade and title claims are detected, never rewritten. The claim types
        ride out on result["unverified_claims"] and the client shows an amber
        advisory. The instructor sees what the model claimed, which is what
        lets them recognise it as wrong (bug #12's failure shape).
      - Canvas ID claims REMAIN destructive. A wrong ID is qualitatively
        different: it can misroute a later write to the wrong assignment or
        student. Rewritten to "[ID redacted]".

ARCHITECTURE DELTA
    * A privacy control that mutated user-facing output became a trust signal
      attached to it. Redaction now happens ONLY on the inbound path.
    * New backend->frontend contract field: unverified_claims: string[].
      Emitted only when non-empty, so ordinary replies carry no extra payload.
    * The frontend banner is CLAIM-TYPE AGNOSTIC: AssistantMessage keys off
      message.unverifiedClaims?.length, not on specific strings. The backend
      can add claim types without a frontend change.
    * "grounded" was deliberately left as set-only-when-true. Making it always
      present broke an exact-payload test (test_plain_text_model_reply_is_
      returned) — the response shape is asserted literally in places.

*** SRP WARNINGS ***
  ! student_context.py holds TWO responsibilities that look like one. Keep them

      - inbound minimization  (llm_safe_*, _PII_KEYS)      -> may redact
      - outbound grounding    (ground_assistant_result)    -> must NOT redact,
                                                              except IDs
    Adding any new "[... redacted]" substitution to the outbound half
    re-creates bugs #2 and #13. If a reviewer asks for redaction of a new
    field, that request belongs in the inbound half.
  ! ground_assistant_result has EXACTLY ONE call site (services/chat.py:3451),
    at the end of every chat turn. It is not workflow-specific and must not be

P1 — THE BLANKET intent_preview EXEMPTION WAS TOO BROAD, AND WAS A REGRESSION
    12cd0d0d exempted every intent_preview from scrubbing on the stated
    grounds that its summary is server text built by services/write_preview.py.
    That is true for only ONE of the two producers:

      services/chat.py  (5 sites: :1201, :1597, :1710, :1845, :3750)
          summary = preview_metadata["summary"]      <- SERVER text
      mcp_tools/dispatcher.py  (generic `case "intent_preview":`, ~:1303)
          summary = action.summary                   <- THE MODEL'S OWN TEXT

    dispatcher.py's case is labelled in its own comment as "PATH A: build the
    write preview here" — it is the PRIMARY write preview path, not an edge
    case. IntentPreviewAction.summary is a plain str the LLM fills in; the
    system prompt at chat.py:2448 instructs it to. The frontend renders
    reply.summary, not preview_metadata.summary.

    Worse: on develop the scrubbing loop had NO gate at all, so intent_preview
    summaries WERE scrubbed. The blanket exemption therefore REMOVED existing
    protection from the exact text an instructor approves a Canvas write from.

    Fix: distinguish the two by whether summary IS the string write_preview
    produced:

        if result.get("intent_preview"):
            metadata = result.get("preview_metadata")
            server_summary = metadata.get("summary") if isinstance(metadata, dict) else None
            return result.get("summary") != server_summary

    Deciding this from the PAYLOAD rather than adding a marker field is
    deliberate and load-bearing: chat.py:1849 persists its result via
    log_message BEFORE grounding runs, and handle_modified_action (chat.py:3650)
    never calls ground_assistant_result at all. A marker key would have leaked
    into stored message JSON (which _load_stored_intent_preview reads back) and
    into that response.

P2 — DOUBLE-SIGNALLING ON AN ID-ONLY MISS
    detect_unverified_claims and strip_ungrounded_canvas_id_claims share
    _CANVAS_ID_CLAIM_PATTERN and the same grounded set, so an ID the detector
    finds is ALWAYS one the scrubber redacts. Emitting "canvas_id" in
    unverified_claims therefore made the client warn "figures could not be
    verified... confirm before acting on them" about a figure that had already
    been replaced with "[ID redacted]" and was no longer on screen.

    Fix: subtract _SELF_EVIDENT_CLAIMS before emitting. Grades, which stay
    visible by design, still raise the notice.

ARCHITECTURE DELTA
    * "Who authored this prose" became a derived property of the payload rather
      than an assumption about the action name.
    * unverified_claims is now explicitly "claims still visible in the text",
      not "all claims detected". The two are no longer the same set.

*** SRP WARNINGS ***
  ! action_is_llm_prose INFERS authorship from payload shape. It silently
    flips if anyone:
      - changes dispatcher.py to assign preview_metadata["summary"] into
        summary (would make model previews stop being scrubbed), or
      - changes any chat.py site to post-edit summary after
        generate_write_preview (would make server previews START being
        scrubbed, re-opening bug #2).
    If you touch either producer, re-read this function. There is a test for
    both directions: test_ground_assistant_result_scrubs_model_authored_
    preview_summary and ..._keeps_instructor_authored_preview_summary.
  ! _SELF_EVIDENT_CLAIMS is only correct while detection and scrubbing share a
    pattern and a grounded set. If someone makes detect_unverified_claims
    broader than strip_ungrounded_canvas_id_claims, IDs will be detected,
    suppressed from the banner, and NOT redacted — a silent hole. Keep the two
    functions' inputs identical or change both together.
  ! handle_modified_action does NOT ground its result. If model-authored prose
    ever reaches that path, it is unscrubbed. Currently safe only because
    chat.py:3750 uses preview_metadata["summary"].

3b. The generation hang (c5a00521)
--------------------------------------------------------------------------------
FILES
    app/frontend/src/pages/Instructor/InstructorAssignmentCreatePage.tsx

SYMBOLS
    hasAutoGeneratedRef        (single-flight guard)
    hasEnhancementSettled      (state)
    isEnhancingDescription     (DERIVED, not stored)

WHAT AND WHY
    The spinner never cleared. Two wrong diagnoses were ruled out with
    evidence before the real one was found:
      - "30s adapter timeout / slow reasoning model" — DISPROVED: measured
        POST /assignments/generate-draft returning HTTP 200 in 0.72s.
      - "React StrictMode double-invocation" — DISPROVED by a test that
        asserted exactly one generate call; it passed.

    ACTUAL CAUSE: canvasUrl is derived from useAuth() + useInstitution(), so it
    is undefined on first render and populated a tick later. That dep change
    re-ran the effect while the request was still in flight. The cleanup set
    cancelled = true, and the single-flight ref then REFUSED the second run as
    a duplicate — so nothing was left to clear the spinner or deliver the
    description. A deadlock between a cancellation flag and a de-duplication
    guard.

    Fix: never cancel, always settle, let the ref keep it to one call. Removed
    the cancelled flag and cleanup entirely. Save-draft is disabled while
    isEnhancingDescription, which also closed a second defect: pressing it
    mid-generation created two resumable workflows for the same assignment.

    isEnhancingDescription is DERIVED rather than stored because accessToken
    can settle after mount, and a value computed before that left the spinner
    off for the whole call. It also avoids the react-hooks/set-state-in-effect
    lint rule.

ARCHITECTURE DELTA
    * Establishes a rule for this codebase's async effects: a single-flight ref
      and an in-flight cancel are mutually exclusive. Pick one.

*** SRP WARNINGS ***
  ! The comment above hasAutoGeneratedRef says the ref is "deliberately the
    ONLY guard". Adding a cleanup that cancels the in-flight request
    reintroduces the exact deadlock. This looks like a missing-cleanup bug to
    anyone reading the effect in isolation — it is not. There is a regression
    test: "still settles when canvasUrl resolves mid-flight".
  ! isEnhancingDescription must stay DERIVED. Converting it to useState and
    setting it in the effect body trips react-hooks/set-state-in-effect and
    reopens the accessToken race.
  ! InstructorAssignmentCreatePage.tsx is now the most overloaded file in this
    stack — describe/review stepper, chat handoff, auto-generation effect,
    draft save/resume, workflow linking, and course selection all live here.
    Four of the five branches touch it, so it is also the main conflict site.
    Strongly consider extracting the auto-generation effect into a hook before
    adding anything else to it.
  ! generate_assignment_draft (backend) uses get_active_llm_config ONLY and
    ignores per-instructor instructor_llm_connections, unlike chat which goes
    through resolve_instructor_llm_request. Same model today, so no visible
    effect — but a per-instructor model override will NOT apply to description
    generation until that is reconciled. Untouched here deliberately.

COMMITS
    a3f08b50  Record a workflow and audit row when the assignment form writes

FILES
    app/backend/app/routers/canvas.py            (create_assignment_endpoint)
    app/frontend/src/lib/map-chat-reply.ts
    app/frontend/src/pages/Instructor/InstructorAssignmentCreatePage.tsx
    app/frontend/src/routes/paths.ts
    app/frontend/src/services/assignmentCreator.ts
    app/frontend/src/services/assignments.ts

WHAT AND WHY
    Reported as "the assignment never reached Canvas". Ground truth from the
    Canvas DB disproved that — all three assignments existed (ids 21, 22, 23 in
    Capstone Project). They were workflow_state=unpublished, which is why they
    were not visible; that is a separate teammate's PR and out of scope here.

    Two real defects remained:

    (1) NO AUDIT TRAIL AT ALL. create_assignment_endpoint was a bare
        passthrough to Canvas. Confirmed empirically: three real Canvas writes
        at 05:20, 05:26 and 05:28, newest audit_logs row from 04:29.
        record_write_audit's own docstring says it is "Shared by
        handle_confirmed_action (chat confirm path) and form write endpoints
        (e.g. create_quiz REST)" — assignments were simply missed.

    (2) THE CHAT'S PENDING WORKFLOW WAS NEVER RESOLVED. create_assignment is
        NOT in the form-handoff exclusion set in services/chat.py
        ({"create_quiz","send_message","update_grade"}), so chat opens a
        PENDING Workflow at intent_preview time. The creator page commits
        straight to Canvas, so nothing ever closed it. Workflow history showed
        "pending" for assignments that plainly existed.

    Pre-existing, but section 3 routes far more traffic through the creator
    page, which is why it surfaced now.

    Changes to create_assignment_endpoint (mirrors create_quiz_endpoint):
      - accepts optional conversation_id / preview_message_id query params
      - with them: claims the assistant's pending Workflow via
        _claim_pending_workflow (the same atomic conditional UPDATE
        ... WHERE status='pending' that handle_confirmed_action uses) and
        marks it executed
      - without them: records a standalone executed Workflow
      - either way: calls record_write_audit
      - ownership is checked on the conversation; another instructor's
        conversation_id is a 404

    Frontend threads conversationId/pendingMessageId from the chat handoff
    through approveAssignmentDraft -> createAssignment as query params. The
    workflowLink is OMITTED ENTIRELY on the plain "+ Create Assignment" path
    so that call keeps its original shape.

DESIGN DECISIONS WORTH PRESERVING
    * Claim the existing Workflow rather than always creating a new one.
      Creating a second row would leave the original stuck pending — the
      reported symptom — and double-count the write in history.
    * A settled preview is never rewritten. If the preview was already
      confirmed or cancelled in chat, _claim_pending_workflow returns false and
      the code falls through to a standalone Workflow. The Canvas write has
      already succeeded at that point, so failing after the fact or reopening
      settled history would both be worse.

ARCHITECTURE DELTA
    * Every Canvas assignment write now produces an AuditLog regardless of
      entry point. The REST form endpoint moved from "thin proxy" to
      "transactional boundary that reconciles chat state".
    * Introduces a cross-surface invariant: a pending Workflow opened by chat
      can be claimed by a REST endpoint. Replay safety rests entirely on
      _claim_pending_workflow's conditional UPDATE.

*** SRP WARNINGS ***
  ! create_assignment_endpoint now has THREE responsibilities: the Canvas
    write, workflow reconciliation, and audit. It is a near-copy of
    create_quiz_endpoint. If audit or workflow semantics change in one and not
    the other they will drift silently. If you touch either, diff them against
    each other afterwards. Extracting the shared tail is the better fix.
  ! The form-handoff exclusion set in services/chat.py is COUPLED to this
    endpoint. If anyone "tidies up" by adding create_assignment to
    {"create_quiz","send_message","update_grade"}, chat stops opening a pending
    Workflow and the claim logic here becomes dead code that silently records
    standalone workflows instead. Change one, change both.
  ! _claim_pending_workflow's conditional UPDATE is the ONLY thing making this
    replay-safe. Do not replace it with a read-then-write; two concurrent

5. bugfix/draft-course-persist
   Draft course vs active course
================================================================================

COMMITS
    ea8a844c  Bind saved drafts to their own course instead of the active one

FILES
    app/frontend/src/lib/typed-draft-storage.ts
    app/frontend/src/pages/Instructor/InstructorAssistantPage.tsx
    app/frontend/src/pages/Instructor/InstructorAssignmentCreatePage.tsx
    app/frontend/src/pages/Instructor/InstructorQuizCreatePage.tsx
    app/frontend/src/pages/Instructor/InstructorFeedbackCreatePage.tsx

SYMBOLS
    TypedDraftContent.courseCode / .courseName   (new)
    TypedDraftCourseCandidate                    (new structural type)
    resolveTypedDraftCourseId(content, courses)  (new)
    matchUniqueCourse(), normalizeCourseLabel()  (module-private)
    requiresCourseSelection                      (now a useMemo, was !activeCourse)

WHAT AND WHY
    Saving a preview as a draft and resuming it opened the create form on
    whichever course was ACTIVE AT RESUME TIME, not the course the draft was
    written for.

    ROOT CAUSE: the draft never stored a course at all. stripCanvasIdentifiers
    (see 1b) keeps ids out of localStorage per #1239, so nothing survived the
    save, and handleResumeTypedDraft filled the gap with
    activeCourse.localId unconditionally. Both reported symptoms are one bug —
    the draft's course is not overwritten on a course switch, it is INJECTED
    FRESH on every resume. A draft resumed without switching courses only
    looked correct by coincidence.

    Fix: persist the course's two DISPLAY LABELS and resolve them back to a
    local id against the current course list at resume time. This satisfies
    #1239 (no Canvas id, no local id — only strings Canvas already displays,
    the same category as the studentName / assignmentName the whitelist has
    always allowed).

    BOTH labels are kept because either can change independently: a renamed
    course still resolves on its code, a re-coded one on its name. Code is
    tried first — instructors rename far more often than they re-code.
    Ambiguous matches (two courses sharing a code) resolve to nothing rather
    than to a guess, and fall back to the active course along with drafts that
    predate this change.

    Also removed the blanket `if (!activeCourse) return;` gate on resume: a
    draft that names its own course no longer needs one selected.
    requiresCourseSelection is now "no active course AND no draft self-resolves".

SCOPE NOTE
    MessageDraftPage has NO course selector, so there is no draft-specific
    course to persist there; it keeps today's active-course behaviour. Three
    save sites, not four.

ARCHITECTURE DELTA
    * Drafts became SELF-DESCRIBING. Resume changed from "seed with ambient
      state" to "resolve the draft's own binding, with ambient state as
      fallback".
    * Establishes a pattern for satisfying #1239 without losing referential
      integrity: persist labels, resolve to ids at use time. This is the same
      shape as Mridul's backend course matching, and would compose with an
      alias table if that lands.

*** SRP WARNINGS ***
  ! The RESOLUTION lives in typed-draft-storage.ts but the PRECEDENCE POLICY
    ("draft's course beats active course") lives in InstructorAssistantPage's
    handleResumeTypedDraft. Any NEW resume entry point must apply the same
    precedence or the bug returns for that surface only. If a second caller
    appears, move the precedence into the storage module.
  ! resolveTypedDraftCourseId takes a structural TypedDraftCourseCandidate so
    callers can pass an already-filtered list. InstructorAssistantPage passes
    availableCourses (all courses); the create pages filter to writableCourses.
    Passing a filtered list to the RESOLVER would make a draft for a
    now-unwritable course silently fall back to the active course. Keep the
    resolver's input broad.
  ! Ambiguity resolves to undefined ON PURPOSE. Do not "improve" it to return
    the first match — that reintroduces silent mis-targeting, which is the
    entire bug.
  ! requiresCourseSelection is PANEL-LEVEL, not per-draft. With no active
    course and a mix of resolvable and unresolvable drafts, the banner is
    hidden but unresolvable drafts are still no-ops on click. Making it
    per-draft requires changing DraftWorkspacePanel's props. Known and
    documented, not an oversight.
  ! See also the stripCanvasIdentifiers warning in 1b — courseCode/courseName
    had to be added to that whitelist. The same trap applies to anything else.

================================================================================
THE ONE RULE, IF YOU READ NOTHING ELSE
================================================================================

Three of the defects in this stack were caused by ONE component quietly
acquiring a second responsibility:

  * student_context.py did PII minimization AND output grounding, so a privacy
    control started censoring the instructor's own text (bugs #2, #13).
  * The auto-generation effect did single-flight AND cancellation, so the two
    guards deadlocked and the spinner never cleared.
  * stripCanvasIdentifiers is both a privacy filter AND the de-facto schema for
    what a draft can hold, so adding a field to the type silently dropped it
    on save (bug #6, and the draft-course bug in section 5).

When extending any component below, ask which of its responsibilities you are
extending. If the answer is "a new one", extract instead of adding.
